## 2. 但"slot 0 的分母最小"也是错的——我测了

你的 §2.5 / §3.2 说：slot 0 的分母天生最小，所以最容易被推出界。

本机 ClearEngine，同参数，把 `07c` 解密出来按槽排：

```
### 07c at slot 0 = 0.0375705
###   carried slots: 8448   min 0.0264306   p50 0.0514468   max 0.303622
###   slot 0 rank: 688 of 8448  (8.1% of carried slots are smaller)
###   six smallest carried slots:
###     6580(%16=4,%2048=436)=0.026431   22964(...)=0.026431   12724(...)=0.026431
###     29108(...)=0.026431              436(%16=4,%2048=436)=0.026431   16820(...)=0.026431
```

> **slot 0 排第 688，有 687 个槽比它小。真正的最小值在 `%2048=436`，不在 slot 0。**

（那六个"最小"是同一个值的六份拷贝——`interval_sum` 复制的，见上一份 §2。
真正不同的位置是 `%2048=436`。）

所以如果机制真是"最小的分母被推成负数"，**坏槽应该出现在 `%2048=436`，而且每次跑位置会变**。
实际是每次都在 slot 0。

### 2.1 顺带：机制描述本身也不自洽

你写的是"bootstrap 误差把它**推过 1.0**"。**最小的值被推过的是 0，不是 1。**
而 `07d` 是**逆元**：分母最小的槽，逆元本来就最大——`>1` 出现在那里是算术上应该的，
不一定是 bug。真正的问题是设备的 `07d` 是 5.8e+05 而本机是 0.049，差 1.2e+07 倍。

### 2.2 而且算术也不支持

lift 2 时你的 guard 报 `[0.051, 0.621]`，本机是 `[0.0543, 0.5986]`——**两边的下端几乎一样**。
0.051 距 0 是 **3.27σ**，单槽越界概率 5.4e-04。

> **3/3 全炸，而 3.27σ 说这事一千次跑不到两次。对不上。**

## 3. 剩下的只能是"算子"，而 slot 0 只对一个算子特殊

误差没有结构（§1），输入没有结构（§2），失败却**每次都钉在同一个槽**。
那结构只能来自中间的某个**运算**。

> **共轭是 Galois 自同构 `slot j -> slot -j`。`slot 0` 是它唯一的不动点。**

而 `conjugate` 恰好出现在两处失败的正上方：

| 失败 | 上游的 conjugate |
|---|---|
| `07d` 每次 1 个坏槽、恒在 slot 0 | `numeric.py:471` —— `_restore_magnitude` 里的 `add(ct, conjugate(ct))`，**每轮迭代都调一次** |
| `07a` 三个最差 carried 槽 = **第 5、6、7 号密文的 slot 0** | `softmax.py:367-370` —— 那三个正是 `multiply_1j(subtract(conjugated, merged))` |

**两个互不相干的症状，同一个槽，中间是同一个算子。**

而本机永远看不到它：ClearEngine 的 `conjugate` 就是 numpy 的共轭，精确到机器字长。
**这解释了为什么六次注入 σ 的本机跑全是干净的**——被测的那个算子在本机是精确的。

### 3.1 现有的那条测试为什么可能漏掉

`test_doubling_through_the_conjugate` 已经在测 `add(ct, conjugate(ct))`，但
它跑在 **SMALL 参数（log_n=13, depth 12）**、用 `scale=0.5` 的稠密随机向量、
断言的是**全局 max 误差 < 1e-5**。

三个都可能让它漏：参数不是 bench 的 log_n=16；一个槽的相对误差在
32768 个健康槽设定的 max-norm 里未必显形；迭代里的量级（0.026–0.9）和 level（剩几个）都不同。
