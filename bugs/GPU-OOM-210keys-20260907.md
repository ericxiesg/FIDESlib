# GPU Benchmark Bug: 210 rotation keys + bootstrap → OOM during key generation

日期：2026-09-07，commit `4e34444`（远程 fix 之后）。分支 `bootstrap-dev`。
远程 V100 (Quadro GV100 32GB, sm_70, CUDA 12.9)。

## 现象

`depth=50, dnum=4, log_n=16, bootstrap_level_budget=(3,3), SPARSE_TERNARY`，
`plan_rotation_keys(scope="layer")` 生成 210 个 rotation index。

Engine 创建时 GPU OOM：

```
Adding bootstrap precomputation to GPU for 32768 slots.
Plaintexts loaded: 378 ~ 10395MB
[FIDESlib] bootstrap key level plan: 0 of 48 keys truncated to level 38 ...
Rotation keys loaded: 49 ~ 12152MB
[FIDESlib] key memory: 49 rotation keys + eval key, resident 12400 MiB, 0 truncated
```

然后在 `AddRotationKeys`（生成 210 个 rotation keys）时：

```
KeySwitchingKey::Initialize
  → RNSPoly::generateDecompAndDigit
    → LimbPartition::generateAllDigitLimb
      → LimbPartition::generate
        → Limb ctor → VectorGPU → GPUmalloc
Cuda failure CudaUtils.cu:400: 'out of memory'
```

## 显存分析

| 组件 | 占用 |
|------|-----:|
| Bootstrap plaintexts | 10.4 GB |
| Bootstrap + rotation keys (前 49 个) | 12.4 GB |
| 剩余 161 个 rotation keys (估算) | ~20 GB |
| **总计** | **~42 GB** > 32 GB |

`SetRotationKeyLevels` 已调用（210 个 index 都有 level plan），但日志显示 **0 truncated**，
说明 level-truncation 机制在当前参数下没有实际缩减 key 大小。

## 已验证可行的单独操作

| 测试 | 结果 |
|------|------|
| Engine (depth=50, dnum=4, 无 bootstrap) | OK，1.7 GB |
| Engine (depth=50, dnum=4, 有 bootstrap) | OK，12.4 GB |
| `multiply_1j` at depth=50, dnum=4 | OK，err ~1e-9 |
| 109 pytest (含 GPU) | 109 passed |
| `plan_rotation_keys(scope="layer", depth=50, bl=40)` | OK，210 keys |

## 复现

```python
import pyfideslib, numpy as np
e = pyfideslib.Engine("cuda:0", log_n=16, depth=50, scaling_bits=50,
                      first_mod_bits=55, dnum=4,
                      rotation_indexes={i: 40 for i in range(1, 211)},  # 210 keys
                      bootstrap_level_budget=(3, 3),
                      secret_key_dist=pyfideslib.SPARSE_TERNARY)
# → OOM during AddRotationKeys
```

## 建议

1. **Key 按需加载**：当前 `AddRotationKeys` 一次性生成所有 210 个 key。如果 key 能在首次使用时
   lazy-load，或分批加载/卸载，峰值显存会大幅下降。
2. **Level-truncation 实际生效**：日志显示 `0 truncated`。`SetRotationKeyLevels` 的 level plan
   最高 level 是 40（depth=50 - bootstrap_level=40 = 10 levels 的 key），但 key 似乎没有按 level
   截断存储。如果 truncation 生效，每个 key 的大小应减少 ~20%。
3. **Bootstrap key 和 rotation key 共享 aux poly 池**：bootstrap 的 378 个 plaintext 占 10.4 GB，
   和 rotation keys 的 LimbPartition 共享 GPU 内存可能冲突。
4. **降低 log_n**：`log_n=13` (N=8192, 4096 slots) 会将每个 key 缩小 8 倍，但 THOR_BERT 需要
   32768 slots（`pack=16, dim=128, n_slot=16` → `slot_count=32768`），无法缩小。
