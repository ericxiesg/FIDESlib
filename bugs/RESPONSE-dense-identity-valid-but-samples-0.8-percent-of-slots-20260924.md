# Dense 恒等测试有效,覆盖缺口补上了——但它只看了 32768 个 slot 里的前 256 个

2026-09-24,针对 `9f06746`。

## 0. 先确认:这个测试是有效的,而且补上了我提的缺口

逐行读完了(不是 grep):

- `slots = cc->GetRingDimension() / 2` = **32768**,生产配置 ✓
- `EvalBootstrapSetup({3,3}, {0,0}, slots)` —— levelBudget 和 dim1 都是生产的 ✓
- `slots < GPUcc.N/2` 为假 → **走 dense 分支** ✓,正是 `744a883` §3 指出缺的那条
- 输入 `x1[i] = 1.0 + i` 全部 ≥ 1,过滤条件 `|x1[i]| > 1e-10` 一个都没滤掉
- `ratios.size()` = 256,**不是空过**

**`spread < 2e-9` 在生产配置下是真结果。`744a883` §3 那条缺口我撤回。**

(顺带:spread 从 32 slot 的 <1e-12 涨到 32768 slot 的 <2e-9,涨了约 1000 倍。这本身可能没什么——操作数多了——但如果后面要做趋势判断,这个数值得记着。)

## 1. 但采样窗口是前 256 个 slot,占 0.8%

```cpp
int checkCount = std::min(256, slots);          // = 256
for (int i = 0; i < checkCount && ...; i++) {
    ratios.push_back(outReal / x1[i]);
}
```

**32768 个 slot 里只检查了前 256 个。**

而这个窗口**恰好排除了历史上所有测到过异常的 slot**(只剩 slot 0 和 1):

| 来源 | 异常 slot |
|---|---|
| multiply 损坏集 | 0, 1, **9891**, **19782**, **20170** |
| CtS 异常集 | 0, **16687** |

**除了 0 和 1,全部 > 256。**

还有一条:`RESPONSE-bootstrap-precision-diagnostic-20260915.md` 那个 **period-2048** 结构(`slot%2048` 的散布是 `slot%16` 的 23 倍)——**在一个 256 宽的窗口里根本看不见一个周期**。

所以这个 PASS 说的是:**"前 256 个 slot 上,复合是 `c·I`"**。它没有排除一个只在高位 slot 上发作的缺陷,而我们**已知**异常就发生在那些位置。

**改法很便宜**:`checkCount = slots`(全查,32768 次除法和一次 min/max,相对于一次 bootstrap 可以忽略),或者至少跨整个范围采样(比如步长 128,覆盖所有 2048 的相位)。

## 2. `744a883` §1 那条**不受影响**,仍然成立

复合测试分不开两个因子:

> `StC∘CtS = c·I` 与 `CtS = M`、`StC = c·M⁻¹` 完全相容。

CtS 和 StC 是**同一份预计算的两个方向**,走**同一个 `LinearTransform()`**、同一套 AFFINE_LT 递延逻辑。那套逻辑里的系统性偏差会同时出现在两个方向,并在复合时精确抵消。

而且我们有直接证据说 CtS 偏了:`CoeffsToSlots` 独立测试拿 GPU 对 **OpenFHE CPU** 比,**22–26×,45 bit 参照,生产路径**。

**恒等测试和那个红是相容的,不是矛盾的。** 所以它清白不了 CtS。
