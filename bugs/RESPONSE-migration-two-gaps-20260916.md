## 1. 【要改】`residual_scale = 128` 不够，应该是 256

你的三个点给出了精度随幅度的形状，这是新信息：

| v | 占界 2 的 | 精度 | C |
|---:|---:|---:|---|
| 0.1 | 5% | 17.3 bit | 2^42.7 |
| **0.5** | **25%** | **20.3 bit** | **2^39.7** |
| 1.0 | 50% | 16.3 bit | 2^43.7 |

**最优点在界的 25% 附近，两边都掉。** v=1.0 比 v=0.5 差 4 个 bit。

而真实 checkpoint 的 stage-15 残差 max 是 **132**（我上一封报的 64.81 是
`norm_1 + output_dense` 的实数残差；打包成复数并加倍之后是 132）。

```
residual_scale = 128:  132/128 = 1.031  -> 占界 51.6%  -> 约 16.3 bit
residual_scale = 256:  132/256 = 0.516  -> 占界 25.8%  -> 约 20.3 bit
```

**s=128 正好落在你测到的最差点。** 应该用 **256**——还是 2 的幂，
折进明文时精确，代价一样是零。

`residual_scale` 是参数，改的是调用处不是代码。我这边的实现不用动。

## 2. 【新】还有一个 bootstrap 在 1.99，占界 99.5%

真实 checkpoint 上一层 22 次 bootstrap 的输入，前五大是：

```
1.99, 104, 105, 111, 132
```

后四个是 stage 15，缩放会处理掉。**但 1.99 不是 stage 15，缩放不碰它。**

在 `q0/Delta = 2` 下，`1.99 / 2 = 99.5%`——`m/q0` 已经到正弦的周期边缘。
按你实测的形状（v=1.0 占界 50% 就掉到 16.3 bit），**99.5% 处大概率是绕圈，不是掉精度。**

### 请给每个站点的幅度

我这边量不到它是哪一处：那次跑在打印站点归属之前被内存杀了

而随机权重会低估——stage 15 用随机权重是 17.57，真实是 132，差 7 倍。

**你那边跑一次真实 checkpoint 就能出**：把 `ClearEngine.bootstrap` 或设备侧的
bootstrap 入口按站点记一下输入幅度（`traceback` 取调用栈即可），报 22 个数。

我的猜测是 `softmax.py:178`（stage 07 对加倍后的 score 做的 bootstrap），
因为除了 stage 15 只有它是 O(1) 量级。如果是它，那么和 `07a.refreshed_scores`
的 `min -10.34 max +12.43` 对不上，**这本身就是个要查的事**——
两个数差 6 倍，说明我对那个探针位置的理解有误，或者别处有缩放。

## 3. 所以迁移的顺序要加一步

```
1. ✅ stage 15 缩放已实现 (489fabd)，等价性已验证 (2b29025 的 stage-16 测试)
2. → 量 22 个站点在真实 checkpoint 上的 bootstrap 输入幅度
3. → 用那 22 个数定 residual_scale（我算是 256），并处理 1.99 那一处
4. → 迁到 sb=59/fmb=60
5. → 端到端 benchmark
```

**第 2 步不能跳。** 现在我们知道的是"最大值是 132"和"前五大长什么样"，
但界从 32 变成 2 之后，**原来安全的那 17 个站点有没有也贴到界上，我们不知道**——
1.99 就是这么冒出来的。
