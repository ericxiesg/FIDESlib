## 1. 为什么 stage 2 的「很小」不是正常

CoeffsToSlots 之后，每个槽装的是原消息的一个系数。对一个随机-ish 的分母，
**没有理由某个系数比中位数小三个数量级**。0.0536 是典型值，7.39e-05 不是「小」，
是**差了 725 倍**。

而且它正好落在后面唯一出问题的那个槽上。**两件事同时发生在 slot 0，不太可能是巧合。**

### 1.1 这也解释了 EvalMod 为什么会放大它

EvalMod 是 `sin(2πx)/(2π)` 的 Chebyshev 逼近 + double-angle 迭代（`SPARSE_TERNARY`
下是 3 次）。逼近在**整个拟合区间**上有一个大致均匀的**绝对**误差；
对一个本该是 0.05 的槽，这个绝对误差可以忽略，
**对一个只有 7e-05 的槽，同样的绝对误差就是 100% 以上的相对误差**。

double-angle 每一轮都平方，把相对误差继续放大。
**所以 776 倍不需要 EvalMod 有 bug——一个异常小的输入就够了。**

> **修 EvalMod 大概率是修错地方。要查的是 CoeffsToSlots 为什么让 slot 0 塌掉。**

---

## 2. stage 4 回到 1.31 倍也是能解释的，而且支持这个读法

SlotsToCoeffs 把槽映回系数。**一个坏掉的槽经过 StC 会摊开到所有系数上**——
这正是我上一份报告里那条：槽域的量经过线性变换回到系数域，就不再集中。

所以 stage 4 的 1.31 倍**不代表问题消失了**，只代表它换了表示。
最终 bootstrap 输出里那个误差仍然在，只是摊开了——
然后在后续的乘法里，某种机制又把它重新集中到 slot 0。**那一步还没解释。**

## 3. 建议的下一步：查 CtS 的对角线明文

`EvalCoeffsToSlots` 是一串「旋转 + 乘对角线明文 + 累加」。那些对角线明文是
**预计算的、与密文数据无关的**——完全符合「确定性、位置相关、换数据不换位置」。

如果某条对角线在 slot 0 对应的位置上值是错的（或者为 0），
slot 0 就会系统性地塌掉，**每次 bootstrap 都一样**。

### 3.1 具体怎么查

这些是**明文，不需要密钥**：

1. 把 `RawCiphertext.cu:1359 / 1380` 那批 `result.CtS.at(i).A` / `StC.at(i).A` 的
   对角线明文解码出来；
2. 看 slot 0（以及 9891 / 19782 / 20170）上的值；
3. 和 CPU 侧同一条对角线比对——**CPU 全程干净，所以它是现成的参照**。

**如果某条对角线在 slot 0 上是 0 或明显偏离，就找到了。**

### 3.2 一个更快的预检

在 `bootstrap_stage(x, 2)` 的输出上，把**全部 32768 个槽**按值排序，
看「异常小」的是只有 slot 0，还是 0 / 9891 / 19782 / 20170 这一组。

- **只有 slot 0 塌** → 对角线的单点错误；
- **那一组都塌** → 是某个结构（stride、digit 边界、BSGS 的 baby-step 分组）。

这一步不用改代码，把 stage 2 的输出多打印几个分位数就行。
