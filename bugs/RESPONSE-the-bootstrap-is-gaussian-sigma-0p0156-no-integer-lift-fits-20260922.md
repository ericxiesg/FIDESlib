## 1. 自举误差：幅度完全刻画出来了，σ = 0.0156

你报的三个数：

```
max 0.0649213   p99 0.0401588   p50 0.0105397
```

对一个高斯 `|N(0,σ)|`，这三个数分别是 `4.15σ`（32768 次抽样的期望最大值）、
`2.576σ`、`0.6745σ`。反解：

| | 由你的数反解的 σ |
|---|---|
| p50 0.0105397 / 0.6745 | **0.01563** |
| p99 0.0401588 / 2.576 | **0.01559** |
| max 0.0649213 / 4.15 | **0.01564** |

**三个独立的分位数给出同一个 σ，三位有效数字。** 而

> **σ = 0.0156 = 32 × 2⁻¹¹ = `message_bound` × 2^-11**

正是 xfail 里记的"10.9 bit"。`bench` 的 `--bootstrap-precision-bits` **默认值就是 11**，
所以本机的噪声模型早就校在这个点上了——只是在你这次测出来之前没人验证过。

### 1.1 你的问题 1 的前提不成立

> "bootstrap 误差 max=0.065，如果集中在 slot 0……"

**至少不是"slot 0 上特别大"。** `max/σ = 4.16`，而 32768 次高斯抽样的期望最大值就是
**4.15σ**。如果某个槽的误差系统性地更大，它会表现为重尾，`max/σ` 会明显超过 4.15。
**它一点都不重。**

> 但要说准确：分位数约束的是误差幅度的**边缘分布**，不是槽之间的**相关结构**。
> 把同一批误差在槽之间任意置换，三个分位数一模一样。所以这否掉的是
> "slot 0 有个特别大的离群误差"，**不是**"误差完全没有结构"。
> §6 的 seed 扫描说明后者恐怕还不能排除。

`%0` 那个模式本身另有来源，见 §2。

### 1.2 但你漏了一行

那条 pytest 还打了 `worst`（误差最大的 5 个槽的 index 和它们的 `%16`/`%2048`），
报告里没有。§1.1 已经基本回答了这个问题，但那一行是直接证据，**下次跑麻烦带上**。

## 2. `%0` 是一个值的 16 份拷贝，不是 16 个坏槽

`_sum_over_groups` 最后一步是 `interval_sum(total, group_size)`，而 `interval_sum`
把向量按 `interval` 折叠**到每个窗口都持有总和**。于是

> **slot `j` 和 slot `j + 2048k` 在这之后恒等。**

你报的 `07e worst at 6144(%0), 28672(%0), 30720(%0)`——6144 = 3×2048，
28672 = 14×2048，30720 = 15×2048。**三个都是 `≡ 0 (mod 2048)`，
所以它们是同一个数的三份拷贝**，`argsort` 从 16 份里挑了 3 份。

真正的信息是：**坏的是"组内第 0 个位置"这一个位置**，不是 16 个槽。

## 3. 没有任何整数 lift 放得下

### 3.1 先撤回：我上次让你跑 lift 2，错了

Goldschmidt 两端都是悬崖：`b < 0` 发散，`b > 1 + e` 让 `2 − k·b` 变号也发散。
而自举误差是**加在 lift 之后、迭代之前**的，所以两端都要留 σ 的余量。

用你 run A 的 guard 观测 `[0.051, 0.621]`（lift 2，所以未 lift 是 `[0.0255, 0.3105]`）：

| lift | 区间 | 下端距 0 | 上端距 1 |
|---|---|---|---|
| 2 | [0.0510, 0.6210] | **3.3σ** ⚠️ | 24σ ✅ |
| 3 | [0.0765, 0.9315] | 4.9σ ✅ | **4.4σ** ⚠️ |

**lift 2 下端太近，lift 3 上端太近。** 和你实测的完全一致：

| | 你观测的 07d 坏槽数 |
|---|---|
| lift 2 | **2 个** |
| lift 3 | **1 个** |

**两个都不为零，在相反的两端。** 这不是"哪个更好"的问题，是**整数网格上没有安全点**。

### 3.2 可行区间

要两端都留 ~4.7σ（8448 个 carried 槽里 99% 概率一个都不越界），需要

```
下端 > 0.0736   且   上端 < 0.9264
→ lift ∈ [2.89, 2.98]
→ 其中的整数：无
```

（这个区间取了最保守的算法——把"最小槽的风险"按到全部 8448 个槽上。
真实值取决于分母在下端附近堆了多少槽，那是我没测的量；
**但你的实测坏槽数 2 和 1 就是这个量的直接测量，两个都 > 0。**）

### 3.3 修法：提精度，不是调 lift

在最好的整数 lift（3）上，两端分别是 4.9σ 和 4.4σ。**一轮 Meta-BTS 把 σ 减半：**

| | 下端 | 上端 | 单槽越界概率（上端） |
|---|---|---|---|
| 现在 σ=0.0156 | 4.9σ | 4.4σ | **5.6e-06** |
| 一轮 Meta-BTS | **9.8σ** | **8.8σ** | **8.0e-19** |
| 两轮 | 19.6σ | 17.6σ | — |

**一轮就把余量从 4.5σ 推到 9σ，单槽越界概率降 13 个数量级。**
而 `report-compute.md` §8 已经给过价：bootstrap 是 **189 ms/次**，
Meta-BTS 的 +4 次/层 = **+0.76 s/层**。**精度方案不受速度约束。**

> 诚实交代一处偏差：按高斯模型，lift 3 应该期望约 **0.05** 个坏槽，你实测 **1** 个，
> 差 20 倍。可能是分母的真实两端比 run A 那次更宽（它每次跑都在动），
> 也可能是尾巴比高斯厚。**但 4.5σ → 9σ 这个结论对 20 倍的模型误差完全不敏感。**

## 4. variance 8.4e7：不是 scale 问题，是自举的**模回绕**

### 4.1 本机同代码、同参数给 0.398

```
本机 ClearEngine（σ=0.0156 的噪声模型）    11a.variance max 0.3982   he_invsqrt [0.119, 0.398] ✅
设备                                        11a.variance max 8.41e+07                        ❌
```

**同一份代码、同一个窗口 `[0.081, 1]`，本机在窗口内。** 所以不是"窗口写错了"，
也不是"少了一个归一化"——`VARIANT_BOUNDS` 是对的。

### 4.2 为什么它在三次跑里几乎不动

这是最关键的线索，你的报告里已经有了但没往下推：

| 跑 | `07e`（softmax 输出） | `11a.variance` |
|---|---|---|
| `633ede0` | 1.089e+12 | 8.841e+07 |
| A (lift 2) | **4.019e+30** | 8.41e+07 |
| B (lift 3) | 4.099e+11 | 8.79e+07 |

**上游跨了 19 个数量级，variance 纹丝不动。** 所以它**不是**简单继承的。

机制是自举的模回绕。自举用正弦逼近模约简，而那个约简**以 `message_bound` 为周期**
（`clear.py` 里 `fold(x) = x − 32·round(x/32)`，这也是本机噪声模型能复现
*灾难性*失败而不只是渐进失真的原因）。于是：

```
softmax 吐出 1e30  →  下一次自举把它替换成它的余数，落进 [−16, 16]
                   →  residual_scale = 256 再乘回去  →  ±4096
                   →  variance ~ 4096²/3 ≈ 5.6e+06，乘 ACTIVATION_SCALE² = 4 → 2.2e+07
```

**和实测的 8.4e+07 同一个量级。** 而且因为回绕把幅度信息整个抹掉了，
**1e12 和 1e30 回绕之后是同样的垃圾**——这正好解释了那三个几乎相同的 8.5e+07。

> **结论：修好 softmax，variance 自己就回来了。** 现在不要动 `VARIANT_BOUNDS`。

## 5. 你的问题 3：不能 clamp

> "能不能在传给 `update_inv_D` 之前把 >1 的槽 clamp 到 1？"

**不能。** CKKS 上没有比较运算。`min(x, 1)` 要先算 `sign(x−1)`，而 `sign` 在 CKKS 里
是一个高次多项式逼近——要有用的精度通常要 **10–20 个 level**。
而我们现在的账是**一层 36 level、卡上只有 38**，本来就差 3 个。**买不起。**

（而且 clamp 会把"哪个槽坏了"这个信息一起抹掉，下次就更难查。）

**同样的钱花在 Meta-BTS 上是 +4 次自举 = +0.76 s/层、0 个 level**，
而且它治的是病因。

## 6. 本机**没能**复现设备——三个 seed 全干净

你测出 σ 之后，本机的噪声模型就是校准过的了：

```bash
python -m thorfhe.bench fhe --engine clear --noise-model --bootstrap-noise-only \
    --depth 41 --layers 1 --limit 1 --per-stage --check-ranges warn --inverse-lift 2 ...
```

`--bootstrap-precision-bits` 默认 11，正是 σ=0.0156。

**三个 seed 全是干净的：**

| seed | `07d.inverse_denominator` max | 设备 |
|---|---|---|
| 0 | 0.229 | |
| 1 | 0.1916 | |
| 2 | 0.1717 | |
| 设备 (lift 2) | | **2.497e+15** |

（seed 3、4 还在跑，出来补。）

seed 0 那次 `inv_input_lift2` 的 **min 是 0.01302**——guard 在自举前看到的下端是
0.0543，自举把它推到 0.013，**即 −2.6σ，差一点就过零**。所以机制是对的、余量是薄的，
**但连着三次都没抽中。**

### 6.1 于是这是个诚实的否定结果

> **把设备实测的 σ 原样注入本机，跑三个 seed，一次都没复现出设备的失败。**

两种可能，我分不开：

1. 尾部事件比 1/3 更稀有——那 §3 的高斯模型低估了 20 倍这件事（lift 3 预期 0.05 个坏槽、
   实测 1 个）就是同一个矛盾的另一面；
2. **设备的误差有 σ 之外的结构**——分位数只约束边缘分布，管不了槽间相关性。
   比如误差在槽之间相关、或者在特定位置系统性地偏一个方向，三个分位数都看不出来。

**所以那条 pytest 的 `worst` 行现在更重要了，不是更次要。** 它是目前唯一能看到
结构信息的地方：如果 5 个最差槽的 `%16` / `%2048` 全是 0，第 2 种可能就坐实了，
而且和 §2 的 `%0` 并成一条线。
