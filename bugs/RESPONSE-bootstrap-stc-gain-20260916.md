## 2. StC 的增益 ~200 很可能是固有的

StC 是 DFT 类的线性变换。这类变换对**相干信号**的增益是 1
（所以消息 3.0 原样出来了），但对**非相干噪声**的增益是 `sqrt(N)` 量级。

`sqrt(32768) = 181`。而观测到的增益：

* 按 max：`1.58e-2 / 9.47e-5 = 167`
* 按 p50：`2.61e-3 / 8.40e-6 = 311`

**181 正好夹在中间。**

机制也对得上：stage 3 注入的误差**夹在 CtS 和 StC 之间**，
所以只被 StC 作用一次，只吃到半边归一化——而消息走完了 CtS→StC 的往返，
归一化是配平的。**这解释了为什么信号对而噪声被放大。**

所以"StC 自己在注入噪声"这个说法我认为不对：它是在**放大 stage 3 留下的那 8.4e-6**，
而放大倍数是这类变换的固有性质，不是 bug。

**要证伪很简单**：如果是固有的 `sqrt(N)`，那么换一个 `log_n`（比如 2^14 而不是 2^16）
增益应该按 `sqrt(N)` 变化（181 → 90）。如果增益不变，那才是 StC 自己的问题。
这个实验不贵，值得做一次把它钉死。

## 3. 但真正的结论在别处：**标定修好也不够**

这是本轮最要紧的一条。

我查了 THOR 的源码——**它确实也 bootstrap 分母**：

```python
# THOR/src/thor/he.py:785
b = DeltaCiphertext(self.bootstrap(denominator), delta)
```

所以我们这里是忠实移植，不是我们自己加的。那么 THOR 的分母有多大？
`inv_epsilon = 2^-11 = 4.88e-4` 是 Goldschmidt 要求的**下界**，
所以 THOR 的分母至少是 4.88e-4。

**而我们 bootstrap 的绝对误差 p50 是 1.04e-2。**

```
1.04e-2 / 4.88e-4 = 21
```

**即使把标定完全修好、把分母拉回 THOR 的区间，误差仍然是整个分母的 21 倍。**

也就是说：

* 标定问题（我们的分母 p50 = 7.03e-5，比下界还低 7 倍）是**第二层**；
* **第一层是 bootstrap 的绝对精度，而它现在差得连 THOR 自己的区间都撑不住。**

先修哪个没有悬念了。

## 4. 这让我对 Part21 的建议 #2 改口

我先前在 `report/part21-review-20260915.md` §4 反对过
"Delta 50→59, q0 55→60"，理由是它把消息界从 32 压到 2，
而我们有 4 次 bootstrap 的输入是 17.57（`layernorm.py:172`，stage 15）。

那个反对**作为反对是对的**（不能只改两个常量），但**结论下错了**。
现在看，EasyFHE 选 `q0/Delta = 2` 不是无关紧要的取舍——
**小的界正是他们让 bootstrap 精确到能刷新小值的方式**，而 `he_inv` 恰恰需要这个。

所以建议 #2 从"不要做"改成"**必须做，而 stage 15 的幅度处理是它的前置工作**"。

### 但有一个数必须先量

`first_mod_bits` 那次实验（55→57，`q0/Delta` 32→128）显示**绝对误差不变**。
如果误差不随界缩放，那把界压到 2 也不会让它变小——建议 #2 就白做了。

**区别在于那次只动了 q0，没动 Delta。** EasyFHE 是两个一起动：
`Delta` 从 2^50 抬到 2^59，**抬了 2^9**。

所以要量的是**单独抬 `scaling_bits`**：

```
scaling_bits 50 → 55（first_mod_bits 保持 55 以上，比如 60），重测同样三个值的绝对误差
```

* **误差按 1/Delta 下降（2^5 = 32 倍）** → 建议 #2 成立，值得整包采纳；
* **误差不变** → 误差是消息域的固定量，抬 Delta 没用，要另找。

这和 `first_mod_bits` 那次是同一个套路的另一半，一起就能把"误差由什么决定"完全定下来。

## 6. 顺带：softmax 路径上八个算子此前零直接测试

查了一遍 stage 06/07/08 用到的算子，**有八个只在端到端测试里被间接跑到**，
没有一个直接的调用：`_sum_over_groups`、`_restore_magnitude`、`_accumulate_streamed`、
`align`、`_broadcast_softmax`、`update_inv_D`、`prepare_for_multiply`、`_fold_accumulator`。

这正是"softmax 错了"这个问题反复难以定位的原因之一——端到端测试能说"错了"，
不能说"错在哪个算子"。

`tests/test_softmax_operators.py`（新增，8 条，全部跑在 `ClearEngine` 上、不需要 GPU）
补了其中几条的直接契约：

* `_sum_over_groups` 把 8 个密文和 16 个 group 折成每个 group 都持有的总和
  —— **它产出的正是那个 7.03e-5 的分母**，此前没有任何测试；
* `_restore_magnitude` 必须保持 `ciphertext / delta` 不变（精确算术下是逐位相等），并且确实抬高幅度；
* `_accumulate_streamed` 必须和数组形式 `_accumulate_product` 算出同一个结果
  （故意用逆序喂它），以及对 level 不一致的对角线报错；
* `align` 把操作数降到共同 level 且不改变值。

剩下 `update_inv_D`、`_broadcast_softmax`、`_fold_accumulator` 的布局契约还没补，
它们需要构造 THOR 的打包格式，工作量大一些，下一轮。
