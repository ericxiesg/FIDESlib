## 1. 为什么单槽损坏排除了内存错误

### 1.1 解析理由

CKKS 的槽是 canonical embedding 的求值：

```
slot_j = Σ_i  c_i · ζ^(i·5^j)          对全部 N 个系数求和
```

所以 **`|∂ slot_j / ∂ c_i| = 1`，对每一个 j 都成立**——
一个系数被改动 δ，**每个槽都被改动 |δ|，一视同仁**。
没有哪个系数「属于」某个槽，也没有哪个槽能被单独打中。

指针越界、limb 表短了、special limb 是陈旧数据——**这些全部是系数域/limb 域的损坏**。
它们的共同签名是「**所有槽一起动**」。

### 1.2 数值确认

```
round trip max error: 4.51e-16          （模型本身是准的）

一个系数被改 +1.0     → 槽误差 max 1      p50 1      max/p50 = 1.00  铺开
64 个连续系数被改     → 槽误差 max 15.31  p50 7.36   max/p50 = 2.08  铺开
```

**设备是 13000。** 差四个数量级，而且方向是反的。

> **结论：`07d` 的 slot 0 是一个「值错了」的槽，不是一块「内存坏了」的系数。**

### 1.3 这作废了什么

| 假设 | 提出者 | 现在的状态 |
|---|---|---|
| kernel 按 `meta` 索引越过 `limb` | 你 | ❌ 越界是系数域 → 会铺开 |
| `limbptr` / `DIGITlimbptr` 有效条目不一致 | **我**（架构报告 §9） | ❌ 同上 |
| `SPECIALlimb` 陈旧数据 | 我 | ❌ 你已用两次修复实测排除，现在又多一条理由 |
| `truncate_keys` | 我 | ❌ 早已排除 |
| limb 表 34 vs 38 | 你 | ✅ 是事实，但**与 bug 无关** |

**我们最近四五轮都在系数域里找，而症状说的是槽域。这是我该更早想到的。**

## 2. 你的实验 3 不能作为证据——`stopAfterStage` 很可能没生效

```
stage 1 (ModRaise     ): slot 0 0.705801   others p50 0.529529  max 0.981137
stage 2 (CoeffsToSlots): slot 0 0.705801   others p50 0.529529  max 0.981137
stage 3 (EvalMod      ): slot 0 0.705801   others p50 0.529529  max 0.981137
stage 4 (SlotsToCoeffs): slot 0 0.705801   others p50 0.529529  max 0.981137
```

**四个不同的停止点，输出逐位相同。** 这不可能——ModRaise 之后和 SlotsToCoeffs 之后
是完全不同的密文。**唯一合理的解释是那个参数没起作用。**

我刚把整条链核了一遍，**代码是对的**：

```
bindings.cpp:252   py::arg("stopAfterStage") = -1
CryptoContext.cpp:1778   FIDESlib::CKKS::Bootstrap(*res_gpu, res_gpu->slots, prescaled, stopAfterStage);
Bootstrap.cu:282/294/324/342   if (stopAfterStage == 1/2/3/4) { ...; return; }
```

**所以问题多半在构建**，而且很可能是同一个老坑：
`report-optimization.md §7` 记着 09-21 那次——
「cmake 不追踪 header 依赖 → 增量构建跨 `Bootstrap.cuh` 的签名变化 → ODR 违反」。

**而 `Bootstrap.cuh` 的签名正是为了加 `stopAfterStage` 改的。**
增量构建下，旧的三参数 `Bootstrap` 会被链接进去，第四个参数被静默丢掉——
**症状就是四个 stage 完全一样。**

> **请 `rm -rf build*` 干净重编译后再跑一次实验 3。** 在那之前，
> 「bootstrap 四个阶段都不偏」这个结论不成立——它没有被测过。

## 3. 下一步该往哪找

误差在**槽域**、**确定性**、**与数据无关**（均匀随机和真实分母坏在同样的槽）。
同时满足这三条的东西不多：

**明文。** 预计算的明文向量按构造就是「位置相关、与密文数据无关」的：

- **CtS / StC 的对角线明文**（`RawCiphertext.cu:1334-1380` 那一批 `result.CtS/StC`）；
- bootstrap 用的各种掩码。

如果某个预计算明文在特定槽上的值是错的，那么**每一次 bootstrap、不管输入是什么，
都会在同样的槽上出错**——这正是我们看到的签名。

而且它自然解释了「只在低 level」：`CoeffsToSlots.cu:150` 的 `ct.dropToLevel(ptLevel)`
说明这些明文是按 level 编码的，不同 level 用的是不同的预计算数据。

### 3.1 建议的检查

比对 CtS/StC 的对角线明文在 GPU 和 CPU 两侧的**解码值**，
特别是槽 0 / 9891 / 19782 / 20170 上。**这是明文，不需要密钥，可以直接解码比对。**
