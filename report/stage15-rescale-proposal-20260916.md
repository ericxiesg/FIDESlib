# 两个 bug 的修法互相冲突，除非把 stage 15 的幅度压下去——而那可以不花 level

日期：2026-09-16。承接 `9b15cc6` 的两组实测。

---

## 1. 先更正一个算错的常数

> `error_50 × Delta_50 = 0.0158 × 2^50 = 2^45.66`
> `error_52 × Delta_52 = 0.000575 × 2^52 = 2^45.82`
> **C ≈ 2^45.7，两个配置给出同一个常数。**

算错了：

```
0.0158   × 2^50 = 1.779e13 = 2^44.02
0.000575 × 2^52 = 2.590e12 = 2^41.24
```

**差 2^2.8 ≈ 7 倍，不是同一个常数。误差不是 `C/Delta`。**

### 而这个更正让结论变好，不是变坏

实测两点：`sb=50 -> 11.0 bit`，`sb=52 -> 13.8 bit`。

**Delta 每多 1 bit，精度多 1.40 bit**——比 `1/Delta` 的 1.0 陡。

所以外推到 22 bit（健康的 bootstrap 精度）：

```
(22 - 13.8) / 1.40 = 5.9 bit  ->  scaling_bits = 58
```

**而 EasyFHE 用的是 59，FIDESlib 自己的 bootstrap 例子用的也是 59。**
实测斜率独立落在了它们的选择上。

你按 `1/Delta` 外推得到"需要 scaling_bits=60，会 OOM"——**那个 60 是被低估的斜率推出来的**。
58 比 60 低两个 bit，而 52 已经证明只改 `scaling_bits` 不会 OOM。

**建议：先补一个 `sb=55` 的点。** 两点定不了斜率，三点能。
如果 55 落在 ~17.2 bit（按 1.40 的斜率），外推就可信了。

---

## 2. 但修 Bug 1 会让 Bug 2 无法收拾

你的实测给了软界：

```
v=  1.0 -> rel 6.5%
v= 10.0 -> rel 4.6%
v= 32.0 -> rel 36.5%   (已绕圈)
v=103.9 -> -18.9       (绕多圈)
```

**可用窗口约 `|v| < 10`，即 `q0/Delta` 的 1/3。**

而 `q0` 受 64 位 limb 限制，实际上不超过 2^60。所以 `scaling_bits=58` 时
`q0/Delta <= 4`，可用窗口降到 **`|v| < 1.2`**。

拿真实 checkpoint 的 layer 0 stage-15 残差去比（17664 个坐标）：

| 窗口 | 越界坐标 | 占比 |
|---|---:|---:|
| `\|v\| < 10`（现在，sb=50） | 约 40 | 0.2% |
| **`\|v\| < 1.2`（sb=58）** | **约 6000** | **约 34%** |

**没有任何参数组合能同时满足两边**，因为 `q0 <= 2^60` 是硬顶。
所以**必须把 stage 15 的输入幅度压下去**。

---

## 3. 压幅度可以不花 level

`stage_15` 的输入是 `norm_1 + output_dense`，出口直接进 `stage_16` 的 LayerNorm。

**LayerNorm 对输入尺度不变**（`(v-mean)/sqrt(var+eps)`，分子分母同阶）。
而且 `he_layernorm:82-84` **已经内建了输入缩放**：

```python
max_denominator = (max_var * self.variance_headroom + var_e) * n ** 2
values = value_mask(g, (0.5 if halve else 1.0) / np.sqrt(max_denominator))
masked = [self.rescale(self.multiply(ct, values)) for ct in x]
```

所以机制是现成的，只是参数没往这个方向用。

### 提议：把 `1/s` 折进两个已有的明文里

| 折进哪里 | 代价 |
|---|---|
| `stage_11` 的 `gamma` / `beta`（norm_1 的输出尺度由它们定） | **0 level**，明文，离线编码 |
| `stage_14` 的 `output.dense` 权重和偏置 | **0 level**，明文，离线编码 |

两者都是 `encode_layer` 里已经在编的明文，乘一个常数是免费的。
于是 `stage_15` 的输入整体变成 `1/s`，**不增加任何运算**。

然后 `stage_16` 的三个参数按 `s^2` 调：

```
min_var  /= s**2      max_var  /= s**2      var_e /= s**2
```

`he_invsqrt` 的迭代次数只依赖 `max_var/min_var` 这个**比值**，比值不变，
**所以 level 预算也不变。**

而 `stage_16` 的输出是归一化量（`2*(gamma*(x-mean)/sqrt(var+eps)+beta)`），
尺度不往下一层传——**这个改动是自洽闭合的**。

### s 取多少

真实数据：stage-15 残差 max 64.81。目标是压进 `|v| < 1.2`（sb=58 的窗口），
再留一倍余量：

```
s = 128   ->   64.81/128 = 0.506,  p99 = 0.029
```

取 2 的幂，折进明文时是精确的。

---

## 4. 一个要小心的地方

`he_layernorm:83` 有一行：

```python
halve = min_var > 0.16
```

**这个判断用的是 `min_var` 的绝对值**，而我们要把 `min_var` 除以 `s^2`
（0.2 → 1.2e-5）。那样 `halve` 会从 `True` 翻成 `False`，**行为被静默改掉**。

所以这个标志要从"对缩放后的值做阈值判断"改成一个显式参数，
随 `min_var` 一起传进来。否则这个改动会在一个完全无关的地方出错。

---

## 5. 建议的顺序

1. **补 `sb=55` 这个点**，确认 1.40 bit/bit 的斜率（三点定线，两点不行）；
2. **实现第 3 节的缩放**，先在 `ClearEngine` 上验证 stage 16 的输出不变
   （尺度不变性是精确的，所以这是一个可以逐位对的测试）；
3. 两者都通过之后，再整包迁到 `scaling_bits=58/59`。

**顺序不能反**：先迁参数会把 34% 的坐标打坏，而现在只坏 0.2%。

---

## 6. 关于 THOR 那边的缺口

THOR 在 `q0/Delta = 2` 下 bootstrap 同一个 64.81，而我们查过它
**没有任何缩放**（`encrypt_embedding`、`stage_15`、`forward` 的 stage 14→15 都没有，
两处已知的缩放 `1/512` 和 `1/64` 都不作用于这里）。

**这个缺口我解释不了。** 可能是 desilofhe 的 bootstrap 用了别的技术
（多次迭代、内部的消息缩放），也可能 THOR 在那几个离群坐标上也是坏的而 MRPC 不在乎。

但**它不影响第 3 节的提议**：我们的实测已经证明 64.81 在我们的实现上会绕圈，
不管 THOR 怎么做，我们都得把它压下去。
