## 2. 建议 #3 在 GPU 上是空操作 —— 不能照做

> "设 `numIterations=2, precision=10`（现在是绑定默认 1/0，从没设过）｜改一行｜289× RMSE"

`api/CryptoContext.cpp:1770-1778`，GPU 路径：

```cpp
// GPU path.
this->LoadCiphertext(const_cast<Ciphertext<DCRTPoly>&>(ciphertext));
Ciphertext<DCRTPoly> result = std::make_shared<CiphertextImpl<DCRTPoly>>(*ciphertext);
auto res_gpu = std::static_pointer_cast<FIDESlib::CKKS::Ciphertext>(...);
FIDESlib::CKKS::Bootstrap(*res_gpu, res_gpu->slots, prescaled);   // <- numIterations / precision 都没传
return result;
```

`FIDESlib::CKKS::Bootstrap` 的签名是 `(Ciphertext&, int slots, bool prescaled)`——
**`numIterations` 和 `precision` 只有 CPU 回退路径用**（`:1765` 的
`context->EvalBootstrap(ctImpl, numIterations, precision)`）。

所以在卡上"改一行"不会有任何效果。要拿到 thor-openfhe 那个 289× 的收益，
得先让 GPU 路径实现 meta-bootstrapping，那是 C++ 工作，不是一行参数。

**不过这条值得记下来当成一个 issue**：一个被静默忽略的参数比没有这个参数更糟，
因为它会让人以为设过了。建议至少在 GPU 路径上对非默认值抛异常。

## 3. 建议 #1（固定 secret dist）—— 采纳，而且问题比它说的大 [实测]

Part21 说"任何一次走 Engine 默认的运行会静默跳 3 层"。实际情况是：
**整个 GPU 测试套件都在走默认。**

`tests/conftest.py:32-33` 的共享 fixture：

```python
def engine(device):
    return pf.Engine(device, rotation_indexes=ROTATIONS, **SMALL)
```

而 `SMALL`（`:14`）里没有 `secret_key_dist`，于是落到 `UNIFORM_TERNARY`；
bench 跑的是 `SPARSE_TERNARY`。两者的 **Chebyshev 系数集和 double-angle 次数都不同**
（sparse 3 次 / depth 10，uniform 6 次 / depth 13）。

**也就是说，本该抓 bootstrap 精度问题的那些测试，跑的是另一套近似。**
`test_bootstrap_noise_level.py` 的 `bench_params` 是唯一显式指定的，它的 docstring
也正是为此写的。

**已修**：`conftest.py` 的 `SMALL` 显式指定 `SPARSE_TERNARY`，并写清原因。

**没有改库默认**：`Engine` 保持 `UNIFORM_TERNARY`。那是更保守的安全选择、也是 OpenFHE 的选择；
SPARSE 是 THOR 为性能做的取舍，不该由一个库替调用者做。漂移的根因是**测试没写明**，
不是默认值选错。

## 4. 建议 #2（Δ 50→59, q0 55→60）—— 不是"改两个参数" [实测]

这是最要紧的一条，而且 Part21 自己的表里就有反证——它的第 4 行写着
"消息幅度 vs q0/Δ：我们 32，EasyFHE **2**"。

`q0/Δ` 是 bootstrap 的消息界：ModRaise 之后密文携带 `m + q0·I`，
靠一个只在零附近近似模约简的正弦把 `m` 取回来，所以消息必须**远小于** `q0/Δ`。
从 `(55, 50)` 换到 `(60, 59)`，这个界**从 32 掉到 2**。

我量了整层 22 次 bootstrap 的输入幅度（随机权重、`depth=37`、`refresh_after_dense`）：

| stage | 站点 | n | max \|m\| |
|---|---|---:|---:|
| **output_dense** | **`layernorm.py:172`（stage 15）** | **4** | **17.57** |
| scores | `softmax.py:178` | 4 | 0.3146 |
| attention_dense | `layernorm.py:155` | 4 | 0.1238 |
| intermediate | `feedforward.py:86` | 8 | 0.08626 |
| scores | `numeric.py:190`（he_inv 内） | 2 | 0.0069 / 0.00022 |

中位数 **0.12**，但有 4 次是 **17.57**：

* 对 `q0/Δ = 32`（现在）：**0/22 越界**
* 对 `q0/Δ = 2`（建议 #2）：**4/22 越界，超出 8.8 倍**

而且这个加倍**是有意的**，`stage_15_prepare_layernorm` 的 docstring 写着：

> "Unlike stage 13 there is no compensating halving, so this returns **twice** the residual.
> That is deliberate: `variance_window` accepts four times the variance for the variants that
> halve their input."

所以采用 EasyFHE 的 Δ **不是改两个常量**，它要求先重做 stage 15 的幅度处理
（以及复核其余每一处）。**这和我们先前的结论一致：EasyFHE 的参数必须整包采纳，不能挑着拿。**

### 顺带纠正一个概念混淆

Part21 说 Δ 50→59 是 "+9 bit 精度"。那是**算术精度**（rescale 取整相对 Δ 更小），
不是 **bootstrap 精度**。而这份报告的主题是后者——对 bootstrap 来说，
**给定消息幅度下 `q0/Δ` 更小是更差，不是更好**。两者方向相反，不能合并成一个"+9 bit"。

## 5. 一个 Part21 没有的数，可能比它讨论的都重要 [实测]

上表里 `layernorm.py:172` 的 17.57，**是我们自己那个界 32 的 55%**，
而其余站点都在 0.12 量级——**差 140 倍**。

这很可能就是 `RESPONSE-bootstrap-precision-20260915.md` 在找的东西的一部分：
bootstrap 的精度随 `|m| / q0` 上升而恶化，而我们有一处站在 55% 上。

**但要注意一个判别**：远端放宽容差的那个测试用的值是 `{2.0, -3.0, 0.5}`，
相对 32 都很小。**如果 bootstrap 在这些小值上就已经不准，那就不是幅度问题，是实现问题**，
和 stage 15 无关。所以两件事要分开量：

1. bootstrap 一个 `{2.0, -3.0, 0.5}` 的常量，看绝对误差 —— 定"实现准不准"；
2. bootstrap 一个幅度 17.57 的常量，看绝对误差 —— 定"stage 15 那一处是不是额外的坑"。

两个数一起给出来，就能分清。这两条已经加进给远端的请求里。

## 7. 建议 #5（diff EasyFHE 的自举位置）—— 同意方向

"EasyFHE 用 depth 30 / post-bootstrap 14 跑完同一条电路，我们要 37 / 20"——
这个差值如果能补上，每把密钥省 28 MiB，是几 GiB 的量级，确实比 level budget 值钱。

它点名的 `evaluate_inverse_sqrt` 里那条自适应刷新
（`if denominator.state.cur_limbs < 8: bootstrap`）值得先看，
因为我们的 `he_invsqrt` 是固定在第 2/3 次迭代刷新。

**但先记一条已经吃过的亏**：我先前提过一个 `refresh_after_context` 的类似改动，
在 depth 30/33/36/37 上全都失败，原因是参考实现把"早刷新"和 LayerNorm 的内部自举**耦合在一起**，
不能单独搬一条。所以这件事要按**整段调度**去 diff，不是挑一处刷新点搬过来。
