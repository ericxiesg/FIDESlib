# 消息幅度与 bootstrap 精度是一对矛盾，而 BERT 的离群维把它顶死了

日期：2026-09-16。数据全部来自真实 checkpoint（`textattack/bert-base-uncased-MRPC`）
和真实 MRPC 输入，明文 numpy，无 FHE。**这份报告纠正我自己两处结论。**

---

## 1. 真实 BERT 在 layer 0 各处的幅度

```
tokens 23/128
  embedding (after LN)       max     11.14   p99     1.368   p50    0.3603
layer 0:
  norm_1                     max      62.2   p99     2.633   p50    0.6238
  intermediate (pre-GELU)    max     16.84   p99     5.021   p50     1.935
  output_dense               max     18.81   p99     1.847   p50    0.4034
  stage15 = norm_1+out_dense max     64.81   p99     3.723   p50    0.8660
```

**中位数 0.87，p99 是 3.72，最大值 64.81。** 分布极度重尾。

---

## 2. 重尾来自 4 个已知的 BERT 离群维

按"有多少个坐标越界"来数（layer 0 的 stage 15，17664 个有效坐标）：

| 界 | 越界坐标 | 占比 | 涉及的 feature 维 |
|---|---:|---:|---|
| **16**（= `q0/2Delta`，我们的 textbook 约束） | 16 | 0.091% | **145, 308, 381, 654** |
| **32**（= `q0/Delta`，我加的守卫） | 8 | 0.045% | **308** |
| **2**（EasyFHE 的 `q0/Delta`） | 2146 | **12.1%** | 665 |
| **1**（EasyFHE 的 `q0/2Delta`） | 7686 | **43.5%** | 768（全部） |

**308 和 381 正是量化文献里那两个著名的 BERT-base outlier dimension。**
这不是我们的 bug，是这个模型的已知性质。

---

## 3. 两处纠正我自己

### 3.1 「stage 15 的 bootstrap 输入是 17.57」—— 错了 6 倍，但方向也错

那个数是随机权重（std 0.04）量的。真实值是 **64.81**（打包成复数后 103.9）。

但更要紧的是**我把它说成了"整个 stage 15 超界"**。实际是
**8 个坐标 / 17664，集中在一个维度上**。把它当成"stage 15 坏了"是过度解读——
它是"一个离群维越界"。

### 3.2 「宽界是 bug 的藏身处，不是余量」—— 只对了一半

我在 `bugs/RESPONSE-message-bound-20260916.md` §7 写过这句。
对 **精度** 那条线它成立（bootstrap 的绝对误差随界走）。
但它漏了另一半：**宽界同时是 12% 的坐标没有溢出的原因。**

所以这不是"我们选错了"，是**一对真实的矛盾**：

```
界窄  ->  bootstrap 绝对误差小  ->  he_inv 能刷新 4.88e-4 的分母  （softmax 需要）
界宽  ->  离群维不溢出          ->  stage 15 能刷新 64.81 的残差  （layernorm 需要）
```

**我们现在的 32 是这两者之间的一个位置，而且两边都不够。**

---

## 4. 于是 THOR 那边有一个 ~32 倍的缺口，没有找到

EasyFHE THOR 跑在 `q0/Delta = 2`、SPARSE（`message_scaling_factor = 1.0`，
没有 UNIFORM 那 512 倍的内部缩放）。而它的 stage 15 要 bootstrap 的是同一个模型、
同一个 64.81。

我把能找的都找了：

| 可能的缩放点 | 结果 |
|---|---|
| `data_encoder.py:41` `encrypt_embedding` | **无缩放**，embedding 原样打包加密 |
| `he.py:1448` `stage_15_prepare_layernorm` | **和我们逐行相同**，无减半，直接 bootstrap |
| `forward.py:259-263` stage 14 → 15 之间 | **无缩放** |
| `encode_weights.py:177` `softmax_scale = 1/512` | 只作用于 **key** 权重，我们有 |
| `encode_weights.py:245,255` `scale = 1/64` | 只作用于 **intermediate.dense**，我们有（`GELU_SCALE=64`），而且 GELU 内部会还原，**stage 15 拿不到好处** |

**所以缺口是真的，不是我们漏了某处缩放。** 只剩两种解释：

* **(a)** desilofhe 的 bootstrap 可用范围远大于 `q0/Delta`——那么 `q0/Delta`
  这个界不描述这类实现，我的守卫阈值要按实测重定；
* **(b)** THOR 在那几个离群坐标上也是坏的，而 MRPC 的分类结果不依赖它们。

**(b) 不像能成立**：stage 16 紧接着算方差，而 THOR 的
`he_layernorm2/3` 用的方差窗是 `[0.2, 150]` 和 `[0.75, 2500]`——
那么宽的上界正说明方差是被离群维支配的。离群维坏了，方差就坏了。

---

## 5. 一个实验分开 (a) 和 (b)

在设备上 bootstrap 已知常数，三个幅度：

```python
for v in (1.0, 10.0, 64.81):
    ct  = engine.encrypt(np.full(engine.slots, v, dtype=complex))
    out = np.real(np.asarray(engine.decrypt(engine.bootstrap(ct))))
    print(v, "->", out[0], " abs err", np.max(np.abs(out - v)))
```

* **64.81 出来还是 ~64.81** → (a)。那么 `q0/Delta` 不是可用范围，
  我把守卫改成按实测的范围，并且 stage 15 没问题；
* **64.81 出来是个无关的数** → (b)。那么**我们和 THOR 在那几个离群坐标上都是坏的**，
  而且迁到界为 2 会把 0.045% 变成 12.1%。

这是目前最便宜、信息量最大的一个实验，**三行，不需要改任何参数**。

---

## 6. 对参数迁移的结论

**在 §5 有结果之前，不要迁到 `Delta=2^59, q0=2^60`。**

不是因为"它不好"——而是因为**它会把 0.045% 的越界坐标变成 12.1%**，
这个数现在是量出来的，不是估的。

如果 §5 给出 (a)，那么"界"这个概念本身要重新定义，整个迁移的理由都要重算。
如果给出 (b)，那么**在迁移之前必须先解决离群维的幅度**——
而 THOR 没有给出办法，所以那会是我们自己要发明的东西。

---

## 7. 顺带：`intermediate` 的 16.84 也值得看

`intermediate`（GELU 之前）最大 16.84。THOR 把这一处的权重缩放了 `1/64`，
所以进 GELU 的是 `16.84/64 = 0.26` 量级——**这就是那个 `1/64` 的作用**：
把 GELU 的输入压进多项式拟合的有效区间。

我们有这个缩放。但它说明 THOR **确实会在幅度要紧的地方缩放**——
只是 stage 15 不在其中。这让 §4 的缺口更可疑：THOR 知道怎么处理幅度，
却在 stage 15 没做，那要么是它不需要（(a)），要么是它也没意识到（(b)）。
