# 进度综述：FIDESlib 作为 THOR 的后端引擎

日期：2026-09-08。分支 `bootstrap-dev`。

**一句话**：THOR 的 18 个 stage 全部移植完毕并在精确算术下逐槽验证，单层端到端在真实 BERT 权重和
真实 MRPC 样本上保真到 relRMSE 1.04e-3；**GPU 路径尚未跑完过任何一层**，卡在一个 level 预算与显存
预算不相交的硬约束上。

> 阅读顺序：本文给全局；算法与布局细节在 [`docs/thor_port.md`](../docs/thor_port.md)；
> benchmark 用法在 [`docs/benchmark.md`](../docs/benchmark.md)；
> 当前 TODO 和远程往来在 [`bugs/STATUS.md`](../bugs/STATUS.md)。

## 1. 目标与分层

把 **FIDESlib**（CUDA CKKS，OpenFHE 兼容）改造成 **THOR**（CCS'25，ePrint 2024/1881，BERT-base
加密推理）的同态引擎，替换掉 THOR 依赖的闭源 `desilofhe`。目标硬件：单卡 V100/GV100 32 GB。

```
THOR/src/thor/he.py        参考实现（1609 行，18 个 stage，约 22 个引擎原语）
        ↓ 逐 stage 移植，方法名照抄
python/thorfhe/            本项目：stage 逻辑 + 编码器 + 精确镜像引擎 + benchmark   (4.7k 行)
        ↓ 同一份 stage 代码跑在两种引擎上
python/thorfhe/clear.py    ClearEngine：numpy 精确算术 + 严格 FIXEDMANUAL level/scale 契约
python/pyfideslib/         Engine：pybind11 → fideslib C++ API
        ↓ devices.empty() → OpenFHE CPU 回退；否则 GPU
src/CKKS/*                 FIDESlib CUDA 内核
```

**关键设计决定**：不另造引擎抽象层。stage 代码只依赖一组原语，`ClearEngine` 和 `pyfideslib.Engine`
各自实现它。前者是精确的，所以**任何失败都是调度或代数错误，不可能是 CKKS 噪声**——这是整个项目
调试效率的来源。

## 5. 已验证的数字

**明文基线**（自建分词器 + checkpoint 读取）：64 条 MRPC validation 上 **84.4% / F1 88.6%**，
与 `textattack/bert-base-uncased-MRPC` 公开数字一致。

**单层加密**（第 0 层加密、其余 11 层明文，6 个真实样本）：

| 指标 | 值 |
|---|---:|
| 层输出 relRMSE / 最大绝对误差 | 1.06e-3 / 5.7e-3 |
| logits relRMSE | 6.4e-4 |
| 概率 L1（均值 / 最大） | 2.6e-4 / 1.4e-3 |
| label agreement | 100% |

逐 stage best-fit scale 全部落在 2.0000（softmax 的 1.0023 是 THOR 源码自身的过归一化）。
量级与草稿 `thor-openfhe` 的 v21 口径（RMSE ~1.3e-3、max ~9e-3）一致。

> **口径**：以上全部来自 `ClearEngine`——精确算术 + 严格 FIXEDMANUAL 契约。它证明**调度和代数正确**，
> 不含任何 CKKS 噪声、显存、速度信息。GPU 跑起来会在这之上叠密文噪声。

## 6. 当前阻塞：两个预算不相交

| 墙 | 约束 | 来源 |
|---|---|---|
| **level** | depth ≥ 52 | 一层里最深的链是 37 层（softmax 自举 → GELU），加上 bootstrap 自身约 14 层 |
| **显存** | depth ≤ ~44 | depth 52 预测 35.3 GiB > 32 GiB，且还要留 3 GiB 给 keygen 的临时 buffer |

在 levelBudget (3,3) / 32 GiB 卡上**可行区间为空**。这不是调参能解决的。三条路：

1. **`levelBudget={4,4}`**：唯一未量过的杠杆，同时影响两堵墙（bootstrap 明文变少但 depth 需求变大），
   净效果必须实测。
2. **缩短那 37 层的链**：在 stage 08→13 的数据通路上加一次自举。算法改动，最治本。
3. **拆开 9 GiB 的 "everything else"**：占预算四分之一还多，目前是标定的黑盒。

## 7. 沿途定下来的几件事（都写进了 `docs/thor_port.md`）

* **THOR 的「密文恒为 2 倍」不变量**：每条密文携带的都是它所表示值的两倍。权重编码器折半、bias 在
  `+conj` 加倍之前加入、LayerNorm 从不抵消的加倍把下一层放回同一基准。第 0 层入口必须喂 2 倍
  embedding。GELU 是唯一例外（多项式只在 `[-1,1]` 有效）。
* **softmax 的三个静默错误**：key 缩放（1/64 而非 THOR 的 1/512）、attention mask 是**每个 score
  密文一个明文**（掩码要表达「这个 **key** 位置是 padding」）、窗口要按**分母**而不是逐元素范围标定。
* **`he.py` stage_06 的 accumulator 路由 bug**：`j == 0` 分支按 `i == 0` 路由而非按 wrap 奇偶，
  导致输出密文 1/2/5/6 的分数偏约 32%。本移植用正确规则，并有用例钉住差异。
* **`MAXP = 64` 溢出**：GPU 常量表没有边界检查，`L + K > 64` 会静默污染相邻表——远程报的三个
  「不同的 bug」（NaN / segfault / cudaMemcpy 失败）其实是同一个溢出越走越远。
* **旋转密钥**：一层要 210 个不同索引 = 51 GiB。拆成 2 的幂后 **15 个 key / 3.6 GiB**，
  代价是 4.5 倍旋转次数，数值逐位不变。

## 8. 测试

本机 **85 passed / 40 skipped**（skip 的是需要编译扩展的 GPU 用例）；远程 GPU 上 111 passed。

测试分三层：布局（逐槽对拍线性代数）、调度（严格 FIXEDMANUAL 契约，错了就抛）、
端到端（对拍明文 BERT）。另有 `test_gpu_resource_fixes.py` 专门钉住那些**不改变任何解密值**的
资源类修复（零旋转、掩码明文复用、`pcmm` 流式、负 level、显存模型）——它们不会被精度断言发现。
